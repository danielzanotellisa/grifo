# 0027. Flashcard export as .apkg with an in-house generator

- Status: accepted
- Date: 2026-11-15
- Supersedes: 0025
- Related: 0012, 0013, 0020

## Context
CSV (0025) leaves the note type to the user, has no room for a "Source" field, and its re-import behavior in Noji is unknown. An .apkg carries the note type, fields, decks and GUIDs, and both Anki and Noji import it. The best-known JavaScript generators (genanki-js, mkanki) are AGPL-3.0, forbidden by 0012; anki-apkg-export is MIT but poorly maintained.

## Decision
- Export kind `FLASHCARDS_APKG`, scope document or subject, generated by a worker job.
- Own generator in the export module: SQLite built with sql.js (MIT, WASM) and zipped with fflate (MIT), producing the classic package layout (`collection.anki2` + `media`) as Python's genanki (MIT) does; genanki is the reference for the format, its code is not copied.
- One note type, frozen forever: fixed id, fields `Front`, `Back`, `Source`, simple templates and CSS.
- Note GUID = `ankiGuid(flashcard.id)`; deck names `Subject::Document`; deck ids from `stableIntId(deckName)`; tags for subject, document and page.
- Note modification time = flashcard `updatedAt`, so re-imports update in place.

## Considered options
- CSV (0025): see context.
- genanki-js / mkanki: AGPL.
- anki-apkg-export: unmaintained; a small own generator is easier to keep correct.
- Python genanki in a sidecar: a second language and container for one feature.

## Consequences
The generator is a few hundred lines with its own tests. Import must be verified in Anki desktop, AnkiDroid and Noji, including update-in-place on re-import (P-011). Changing the note type is a breaking change that needs a new ADR.
